# Handover — Thailand nationwide rain nowcasting, V3 + V7 session (2026-08-11)

Continues `capstone_experiments.md` (experiments 01–12) and `handover_2026-08-01.md`. That
session finished the **Bangkok** ladder (56 cells, 9 km). This session built the **nationwide**
equivalent (833 cells, 25 km) end to end: observed labels, a control, and the Himawari IR config.
Experiments 13–15.

## State right now

- **All compute complete.** Nothing running, nothing mid-flight.
- The headline result: **Himawari IR gains +0.040 ROC / +0.084 PR-AUC at h1 @ 1.0 mm** over the
  Open-Meteo baseline, on 1,930,894 wet-season rows. That **exceeds Bangkok's IR-alone gain
  (+0.033)** and matches its full IR+gauges stack (+0.038) — with no gauge data at all.
- **Nothing here is deployable yet.** See "The deployability blocker" below; it applies to the

Three things the wider metric set shows that ROC alone hides:
1. **PR-AUC gains are ~2x the ROC gains** on the rare targets. ROC is imbalance-insensitive; at a
   19% base rate PR-AUC is the honest operational number.
2. **The gain is precision, not recall.** Precision improves at all six targets; recall is flat and
   slightly negative at three. IR suppresses false alarms — it rules out "clear sky, model says rain".
3. **Calibration improves independently** (Brier skill +0.042–0.069 everywhere), which better ranking
   does not imply. Matters if you threshold anywhere other than the F1-optimal point.

## 13 — Labels: the reason this session existed

Every earlier Thailand notebook graded itself against Open-Meteo's own ERA5 `precipitation` — the
same column that generates `precipitation`, `precipitation_lag_*`, `precipitation_sum_past_*` on the
feature side. Measured on identical grid/hour rows, **IMERG cell-mean correlates with that column at
r = 0.12**. Similar wet-hour base rates (44.9% vs 48.5% in the Sept-2025 pilot), near-total
disagreement about *which* hours. So `om_only` was partly learning ERA5's own persistence, and no
observed-rain feature could ever have been measured honestly against it.

**Fix:** new table `IMERG_THAILAND_DATA`, 14,993,167 rows, 833 grids,
local 2024-06-30 07:00 → 2026-07-20 06:00, every hour complete.

- Script: `IMERG_Script/fetch_imerg_thailand_data_gee.py` (~2 h, resumable per chunk).
- **The Bangkok GEE method does not scale and fails outright.** It maps `sampleRegions` over each
  half-hour image and flattens, giving (images x cells) features per request: 48 x 56 = 2,688 at
  Bangkok, inside Earth Engine's 5,000-element limit; 48 x 833 = 39,984 dies with
  `Collection query aborted after accumulating over 5000 elements`. Batching cells does not help
  (220-cell batches still blow it). The port **transposes the reduction**: stack a chunk's images
  with `toBands()` and run `reduceRegions` once over the 833 cells. Element count is then fixed at
  833 regardless of chunk length. Measured ~4 s for a 1-day chunk; ~2.5 s/day at `--chunk-days 3`.
- **Both cell-mean and cell-max are stored.** A 25 km cell spans ~10 IMERG samples, so a point
  sample would reintroduce the point-vs-cell mismatch that capped the V5 gauge gain. Wet-hour base
  rates differ a lot: cell-max 26.9%, cell-mean 17.8%. **We chose cell-max** ("rain anywhere in the
  cell"). Switching is a one-line change in `Thailand_Rain_V3.IMERG_LABEL_COLUMN` + a refetch-free rebuild.
- **UTC/local boundary gotcha:** the fetch range is in UTC days but the panel is local (UTC+7), so a
  run starting at the panel start leaves the first 7 local hours unlabelled. **Always fetch one UTC
  day before the panel start.** Done here (2024-06-30).
- **One hour is genuinely missing from the archive**: local 2026-06-01 12:00 (UTC 05:00–06:00). GEE
  has 46 images that day, not 48. Not recoverable; 833 rows carry NULL labels and the future-window
  guard drops dependents rather than mislabelling them.
- **39% of the panel is provisional** (Late Run, from 2025-10-01), vs 16% at Bangkok.

## 14 — `Thailand_Rain_V3.py`: the nationwide control

Named for the *protocol*, not a lineage. Imports `BKK_Rain_V3`'s CV machinery so numbers stay
readable next to the Bangkok ladder. Four deliberate departures, each forced by scale or geography:

| | Bangkok | Thailand | why |
|---|---|---|---|
| label | IMERG point sample | IMERG **cell-max** | 25 km cell spans ~10 IMERG samples |
| rows | all hours, 2.45 M | **every 4th hour**, 3.74 M of 14.9 M | 14.9 M x 66 float32 peaks ~14 GB; box has 15.6 GB |
| folds | leave-one-year-out | **leave-one-2-month-block-out** (13) | the "years" are Jul–Dec 2024, all 2025, Jan–Jul 2026 — year folds confound season with fold |
| provisional | 16% | 39% | stored per row |

The hour stride subsamples *issue times only*; labels and IR features are built from the full hourly
series, so nothing downstream sees a gappy history.

**`cv` checkpoints after every fit**, not every config. V3/V7 resume at config granularity, fine at
6 folds x 6 targets (~40 min exposure) but not at 13 x 6. Each fold keeps
`oof_fold_<config>_<fold>.npz` with a per-target `done` flag, so a kill costs one partial fit (~2 min).
Per-fit rng seeding (`[RANDOM_STATE, fold, target]`) makes a resumed run bit-identical to an
uninterrupted one — the old single-stream rng would have silently shifted every later fold.

**Result:** pooled ROC 0.86–0.89, but **the pooled number is inflated by climatology** and should not
be quoted alone. Per-block: dry blocks 0.92–0.96 (base rate 1.8–5.0%), wet blocks 0.77–0.80 (base
rate ~20%). A pooled 0.87 blends "tell December from July" with the actual task. **0.77–0.80 is the
operationally meaningful baseline** and is what V7 is measured against.

**The `run_type` breakout in `report` cannot answer the question it was built for.** It shows
provisional scoring *better* than permanent (0.878 vs 0.861 at h1_0.1mm) — but the provisional era
starts October 2025 and is therefore disproportionately dry-season. It measures season, not
detection quality. Same-season pairs across the boundary (2024-11..12 vs 2025-11..12: 0.947 vs 0.922;
2025-01..02 vs 2026-01..02: 0.957 vs 0.928) hint Late Run is slightly *worse* once season is held
fixed — the opposite of the pooled reading.

## 15 — `Thailand_Rain_V7_himawari_ir.py`

Every geometric constant was **measured by probe**, not carried over:

| | Bangkok | Thailand |
|---|---|---|
| segments | 4 | **4 + 5** (3 and 6 decode to zero finite pixels) |
| crop | 72 x 89 px | **797 x 452** = 360,244 px |
| cell radius | 0.08 deg | **0.1126** (25 km) |
| env radius | 0.35 deg | **0.50** (~55 km) |
| per slot | ~1.8 s | **5.5 s** (3.8 s network, 1.5 s decode, 0.2 s stats) |

Coverage 833/833 cells, no coastal or border dropouts.

**Pilot (the reusable pattern, again worth it):** 62-day monsoon fetch (~27 min) + no-training
`screen`. Pre-registered rule *stated before looking*: trained `om_only` sits at 0.77–0.80 on wet
blocks, so a single **untrained** IR signal clearing **0.70** justifies the full download. Result:
0.68–0.76, five of six targets clear. Went ahead; the trained result then matched the prediction.
The winner everywhere is `hw_neg_tbmin_env_lag1` (coldest top in the ~55 km ring, 1 h old) — the
cell-only variant is consistently worse, the signature of convection *approaching* rather than
sitting over a cell, and validation of widening the env radius.

**Fetch:** wet season only (May–Oct, both years) = 388 days, 9,312 slots, ~2.9 h at 4 workers,
~49 GB transferred, 91 MB stored, **56 failed slots (0.6%)**. Resumable per day file — verified
empirically (re-requesting 3 done days: `0 new days`, 1.5 s). S3 throughput swung by a factor of 30
during the run (one ~20 min patch where segment-5 downloads crawled at ~30 KB/s, self-cleared).

**CV scoped to IR-covered blocks.** `covered_folds` measures `hw_valid` per block and keeps those
>= 90%: kept 7 (0, 1, 5, 6, 7, 11, 12), skipped 6 at 0.0–0.5%. Clean split, no ambiguous middle.
42 fits, ~9.9 min/block, 1.6 h total. Registers the config into `Thailand_Rain_V3.CONFIG_BLOCKS` and
calls that module's `run_cv`, so per-fit checkpointing applies here too.

**Per-block gain (h1 @ 1.0 mm) — and the one unexplained result:**

| block | om_only | +IR | gain |
|---|---|---|---|
| 2024-07..08 | 0.772 | 0.815 | +0.042 |
| 2024-09..10 | 0.824 | 0.865 | +0.041 |
| 2025-05..06 | 0.781 | 0.825 | +0.044 |
| 2025-07..08 | 0.796 | 0.842 | +0.046 |
| 2025-09..10 | 0.802 | 0.853 | **+0.052** |
| 2026-05..06 | 0.800 | 0.823 | **+0.023** |
| 2026-07 | 0.779 | 0.795 | **+0.015** |

Five blocks cluster at +0.041–0.052; the two 2026 blocks are half that. **Cause unknown.** It is not
simply provisional IMERG — block 7 is partly Late Run and has the highest gain. Candidates: panel-edge
thinning of `hw_tb_min_env_lag3` / `drop3`, or a change in the Late Run stream during 2026. This is the
most deployment-relevant subset showing the weakest gain, so resolve it before shipping.

## The deployability blocker (applies to Bangkok V7 too)

**The 66 Open-Meteo features are ERA5 reanalysis, not forecast.** Both fetch scripts hit
`archive-api.open-meteo.com/v1/archive`; `OM_BKK_DATA.model` reads `open_meteo_archive`. ERA5 has
~5-day latency — these features cannot be obtained in real time by any means. A deployed model must
be fed forecast-API values, which have different error characteristics (ERA5 has assimilated the
observations that actually happened; a forecast has not). That shift is entirely unquantified.

This means `om_bkk_rain_v7_himawari_ir/deploy/*.joblib` — described in the previous handover as "the
first deployable model files the project has ever had" — **are not deployable as-is either.** The
Himawari and gauge blocks are genuinely real-time; the Open-Meteo features underneath them are not.

**The fix is concrete:** Open-Meteo's historical forecast API
(`historical-forecast-api.open-meteo.com/v1/forecast`) archives what the forecast actually said at
the time. Retraining on that gives train/serve parity.

Other blockers, smaller:
1. **No Thailand artifacts** — no `deploy_fit` phase written (~20 min to write, ~15 min to fit).
2. **Wet-season only.** Dry-season rows were in training but with NaN IR throughout, so real
   dry-season IR at serve time is out of distribution. Either fetch the dry season (~4 h) or gate
   the IR model to May–Oct with `om_only` fallback.
3. **The 2026 decay**, above.
4. **IR–label affinity** (standing caveat): IMERG V07 ingests geostationary IR, so part of the gain
   is affinity with the grader. Deployment-relevant since labels *are* IMERG, but true physical skill
   is lower than +0.040.

## Not done / known gaps

- **No IMERG ceiling for Thailand.** Bangkok could say "60–75% of ceiling"; here there is no trained
  `imerg_offset0h` config, so the gain has no denominator. ~1.5 h to build the history block + 42 fits.
- **No nationwide gauge block.** `TMD_DATA_MERGE` has 85 stations but only lat 13.4–20.4,
  lon 97.9–101.4 — no Isaan, no eastern seaboard, no peninsula. Station *catalogues* for the missing
  regions are loaded (~142 more); only the hourly scrape is missing. Given gauges added just +0.004
  on top of IR at Bangkok, low priority.
- **No terrain features.** 833 static rows (elevation, relief, land fraction, coast distance from
  the already-loaded `thailand_land_boundary`). Bangkok never needed these — 56 flat delta cells. A
  nationwide model spanning sea level to 2,500 m has to infer regime from lat/lon alone, which means
  memorising cells. Cheap and probably worth doing.
- `openmeteo_ecmwf_hres_thailand_weather` / `openmeteo_thailand_core_weather` look useful but hold
  only **2026-05-04 → 2026-05-24** — a 3-week pilot scrape, not a training history.
- **Still not under version control.** `.git` exists but `git status` reports "not a repository".
  Asked for since experiment 08.

## Recommended order

1. **Quantify the reanalysis→forecast gap** (the gate). Pull the historical forecast API for a recent
   month over the same grid, compare feature distributions vs ERA5, score the trained model on
   forecast-fed inputs. If the drop is small, everything else is straightforward; if large, retrain on
   forecast features and every number above shifts.
2. Diagnose the 2026 decay.
3. `deploy_fit` + terrain features.
4. Optional: IMERG ceiling config; dry-season IR fetch.

## Environment notes

- `satpy` and `boto3` were **missing** from `.venv` at session start despite V7 needing them;
  installed. `pip` warns `aiobotocore 3.8.0 requires botocore<1.43.47` — inert here (s3fs is a
  transitive dep, nothing in the project imports it; the fetch downloads to local files via boto3).
- Postgres is **not** used by `cv` — it reads only `.npy` from `_th_cache`. Stopping it frees memory
  during long fits.
- Timing on this box is dominated by memory pressure and swings ~3x. An autovacuum on the freshly
  built 13 GB precompute table tripled fit times for the first fold; use the whole-run average as
  the estimator, never a single fold.
